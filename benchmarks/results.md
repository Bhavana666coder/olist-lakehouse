# Spark on YARN Performance Tuning Study

## 1. Introduction

The purpose of this project is to evaluate the performance of Apache Spark workloads running on Hadoop YARN. The experiments investigate the effects of shuffle partition configuration, broadcast joins, Adaptive Query Execution (AQE), partition pruning, and Parquet file layout.

The experiments use the Olist e-commerce dataset stored in HDFS. Synthetic records are generated by replicating original data to increase the workload size for benchmarking.

## 2. Experimental Setup

- **Dataset:** Olist e-commerce dataset
- **Execution engine:** Apache Spark 3.5.1
- **Cluster manager:** Hadoop YARN
- **Storage:** HDFS
- **File format:** Snappy-compressed Parquet
- **Synthetic replication factor:** 20
- **Executor memory:** 1 GB
- **Executor cores:** 1
- **Executor instances:** 2

### 2.1 Scaled Dataset Sizes

| Dataset | Row Count |
|---|---:|
| Scaled order items | 2,253,000 |
| Scaled orders | 1,988,820 |
| Scaled customers | 1,988,820 |

The scaled records were generated from the original records using a replication factor of 20. These additional rows are synthetic benchmark data, not additional real-world transactions.

## 3. Join and Aggregation Performance

The first experiment measured a join-and-aggregation workload using different Spark configurations. Each configuration joined order items with orders, customers, products, and sellers, then aggregated the results by customer state and product category.

### 3.1 Benchmark Results

| Configuration | Shuffle Partitions | Broadcast Joins | AQE | Aggregate Rows | Runtime (seconds) |
|---|---:|---|---|---:|---:|
| Baseline | 200 | Disabled | Disabled | 1394 | 67.00 |
| Reduced Shuffle | 50 | Disabled | Disabled | 1394 | 34.37 |
| Broadcast Joins | 50 | Enabled | Disabled | 1394 | 31.97 |
| AQE Enabled | 50 | Disabled | Enabled | 1394 | 29.99 |

**Note:** The broadcast configuration explicitly broadcast the products and sellers tables. Automatic broadcast was disabled for these experiments.

### 3.2 Observations

1. Reducing shuffle partitions from 200 to 50 reduced the measured runtime from 67.00 seconds to 34.37 seconds, an improvement of approximately 48.7%.
2. Enabling broadcast joins reduced the measured runtime from 34.37 seconds to 31.97 seconds.
3. Enabling AQE with 50 shuffle partitions and broadcast joins disabled produced a measured runtime of 29.99 seconds.
4. All four configurations returned 1,394 aggregate rows, indicating consistent aggregate output counts across these runs.

These results suggest that tuning shuffle partitions, using broadcast joins, and enabling AQE can improve performance for this workload.

## 4. Partition-Pruning Experiment

This experiment compared reading an unpartitioned Parquet dataset with reading a dataset partitioned by `order_status`.

Both datasets were queried using the filter:

`order_status = 'delivered'`

### 4.1 Results

| Dataset Layout | Delivered Orders | Read and Count Time (seconds) |
|---|---:|---:|
| Unpartitioned Parquet | 96478 | 2.05 |
| Partitioned by `order_status` | 96478 | 1.12 |

### 4.2 Observations

The partitioned dataset completed the measured query in 1.12 seconds, compared with 2.05 seconds for the unpartitioned dataset. This represents an observed runtime reduction of approximately 45.4%.

Both datasets returned 96,478 delivered orders. Partition pruning allows Spark to skip unrelated status partitions when executing a filter on the partition column.

The result suggests that partitioning by a frequently filtered column can improve query performance. However, the measurements represent one run per configuration and may be affected by caching and system load.

## 5. Small-Files Experiment

This experiment investigated the effect of Parquet file layout on read performance. The scaled orders dataset containing 1,988,820 rows was written using two configurations:

- **Many-files layout:** `repartition(200)`
- **Few-files layout:** `coalesce(8)`

The number of generated Parquet files and the time taken to read and count all rows were measured.

### 5.1 Results

| Dataset Layout | Parquet Files | Rows Read | Read Time (seconds) |
|---|---:|---:|---:|
| Many files | 200 | 1988820 | 4.54 |
| Few files | 2 | 1988820 | 0.80 |

### 5.2 Observations

The few-files layout completed the measured read and count operation in 0.80 seconds, compared with 4.54 seconds for the many-files layout. This represents an observed runtime reduction of approximately 82.4%.

Both layouts returned 1,988,820 rows. The few-files layout produced only two Parquet data files, even though `coalesce(8)` was used, because the requested number of partitions does not guarantee that every partition will produce a nonempty output file.

These results suggest that reducing the number of small Parquet files can improve read performance for this workload.

## 6. Overall Findings

The experiments produced the following preliminary findings:

1. Reducing shuffle partitions from 200 to 50 improved the measured join-and-aggregation runtime.
2. Explicitly broadcasting the products and sellers tables improved the measured runtime compared with the 50-partition configuration without broadcast.
3. Enabling AQE produced the shortest measured runtime among the four join-and-aggregation configurations tested.
4. Partitioning orders by `order_status` reduced the measured time for counting delivered orders.
5. Reducing the number of Parquet files improved the measured read-and-count time for the scaled orders dataset.

Across all experiments, the row counts remained consistent between the compared configurations.

## 7. Limitations

- Synthetic rows were generated by replicating original records and do not represent additional real-world transactions.
- The scaled dataset contains 2,253,000 order-item rows using a replication factor of 20.
- Each benchmark configuration was measured once. Repeated trials are needed to assess run-to-run variability and confirm the performance trends.
- Partition-pruning and small-files experiments used the original and scaled orders datasets, respectively.
- Runtime measurements may vary with caching, container resources, scheduling, and system load.
- The experiments were conducted in a resource-limited local Docker and YARN environment. Results may differ on larger clusters.
- These experiments did not include a completed data-skew benchmark or a detailed comparison of Spark UI execution metrics.

## 8. Conclusion

This study evaluated several practical Spark performance-tuning techniques on an Olist e-commerce dataset running on Hadoop YARN.

The measured results showed improvements from reducing shuffle partitions, using broadcast joins, enabling AQE, partitioning data by a frequently filtered column, and reducing the number of Parquet output files.

The results are preliminary because each configuration was measured only once. Repeated trials and additional Spark UI analysis would help validate the findings and provide a more detailed understanding of execution behavior.
